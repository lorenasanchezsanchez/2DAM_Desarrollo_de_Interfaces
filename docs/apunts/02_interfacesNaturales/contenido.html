Concepto de interfaz natural de usuario

Durante décadas, para comunicarnos con un ordenador hemos necesitado aprender su lenguaje: comandos de texto, combinaciones de teclas, clics de ratón en posiciones precisas. El ser humano se adaptaba a la máquina. Las Interfaces Naturales de Usuario (NUI — Natural User Interface) invierten esta relación: son la máquina quien aprende a entender al ser humano en su forma más natural de comunicarse — hablando, gesticulando, mirando, moviéndose o tocando.

El término NUI fue popularizado por investigadores de Microsoft Research en los años 2000 y describe cualquier interfaz que hace desaparecer la tecnología de en medio, permitiendo que el usuario interactúe de forma intuitiva sin aprendizaje previo. Si necesitas leer un manual para saber cómo usar la interfaz, probablemente no es una NUI.

Definición formal

Una Interfaz Natural de Usuario (NUI) es un sistema de interacción persona-máquina que utiliza modalidades de comunicación inherentes al ser humano — voz, gestos, movimiento corporal, expresiones faciales, mirada o tacto multifinger — para interpretar la intención del usuario sin requerir aprendizaje de comandos explícitos, apoyándose habitualmente en técnicas de aprendizaje automático para reconocer y clasificar estas entradas de manera robusta en condiciones del mundo real.

Tipos de interfaces naturales de usuario

Las NUI no son una tecnología única sino un paraguas que agrupa múltiples modalidades de interacción. Cada tipo tiene sus propias características técnicas, requisitos de hardware y casos de uso idóneos. En una aplicación real, es habitual combinar varias modalidades para crear una experiencia más robusta y accesible.

Herramientas de aprendizaje automático aplicadas a UI

Las NUI no serían posibles sin el aprendizaje automático (Machine Learning, ML). Reconocer la voz de una persona en un entorno ruidoso, detectar la posición de 21 puntos de una mano en tiempo real o comprender el significado de una frase en lenguaje natural son problemas demasiado complejos para resolverlos con reglas programadas a mano. El ML aprende a resolverlos a partir de millones de ejemplos.

La buena noticia para nosotros como desarrolladores de apps es que no necesitamos ser científicos de datos para integrar ML en nuestras aplicaciones. Existen librerías que encapsulan modelos pre-entrenados y nos ofrecen APIs de alto nivel que podemos usar directamente en Android.

Concepto de entrenamiento de un modelo

Antes de integrar ML en una app, es fundamental entender qué hay detrás de esas APIs. Un modelo de ML es, en esencia, una función matemática con millones de parámetros (pesos) que ha aprendido a transformar una entrada (imagen, audio, texto) en una salida (clase, etiqueta, probabilidad). El proceso de ajustar esos parámetros usando datos de ejemplo se llama entrenamiento.

Transfer Learning — el atajo del desarrollador de apps

En la práctica, como desarrolladores Android raramente entrenamos modelos desde cero. El Transfer Learning nos permite tomar un modelo ya entrenado en millones de imágenes (como MobileNet, entrenado en ImageNet) y reentrenarlo con solo unos cientos de nuestros propios ejemplos para una tarea específica. Google ofrece Teachable Machine (sin código) y ML Kit Model Maker para hacer exactamente esto. Así podemos crear un clasificador de gestos personalizado en horas en lugar de meses.

2import org.tensorflow.lite.gpu.GpuDelegate
3import java.nio.ByteBuffer
4import java.nio.ByteOrder
5
6class ClasificadorGestos(context: Context) {
7
8    private val interpreter: Interpreter
9    private val etiquetas: List<String>
10
11    init {
12        // 1. Cargar el modelo .tflite desde los assets de la app
13        val modelo = cargarModeloDesdeAssets(context, "modelo_gestos.tflite")
14
15        // 2. Configurar el intérprete con aceleración por GPU
16        val opciones = Interpreter.Options().apply {
17            val gpuDelegate = GpuDelegate()
18            addDelegate(gpuDelegate)         // Usa GPU para la inferencia
19            numThreads = 4                   // Hilos de CPU como fallback
20        }
21        interpreter = Interpreter(modelo, opciones)
22
23        // 3. Cargar etiquetas (clases que puede predecir el modelo)
24        etiquetas = context.assets.open("etiquetas_gestos.txt")
25            .bufferedReader().readLines()
26    }
27
28    // 4. Función principal: recibe los puntos de la mano y devuelve la predicción
29    fun clasificar(puntosLandmark: FloatArray): Resultado {
30        // El modelo espera un array de 63 floats (21 puntos × 3 coordenadas)
31        val entrada = ByteBuffer.allocateDirect(63 * 4).apply {
32            order(ByteOrder.nativeOrder())
33            puntosLandmark.forEach { putFloat(it) }
34            rewind()
35        }
36
37        // La salida es un array de probabilidades (una por gesto)
38        val salida = Array(1) { FloatArray(etiquetas.size) }
39
40        // 5. Ejecutar la inferencia
41        interpreter.run(entrada, salida)
42
43        // 6. Encontrar la clase con mayor probabilidad
44        val probabilidades = salida[0]
45        val indiceMaximo = probabilidades.indices.maxByOrNull { probabilidades[it] } ?: 0
46
47        return Resultado(
48            gesto = etiquetas[indiceMaximo],
49            confianza = probabilidades[indiceMaximo],
50            todasLasProbabilidades = etiquetas.zip(probabilidades.toList()).toMap()
51        )
52    }
53
54    private fun cargarModeloDesdeAssets(context: Context, nombreArchivo: String): ByteBuffer {
55        val descriptor = context.assets.openFd(nombreArchivo)
56        val canal = FileInputStream(descriptor.fileDescriptor).channel
57        return canal.map(FileChannel.MapMode.READ_ONLY, descriptor.startOffset, descriptor.length)
58    }
59}

Reconocimiento de voz

El reconocimiento de voz es, hoy en día, la NUI más extendida y madura. Desde el dictado de mensajes en WhatsApp hasta Alexa controlando tu casa, la tecnología de voz ha abandonado los laboratorios para convertirse en una interfaz cotidiana. Para un desarrollador Android, integrar capacidades de voz en una app es hoy más accesible que nunca.

Voz y habla — conceptos fundamentales

Para implementar reconocimiento de voz correctamente, es útil entender los distintos subproblemas que la cadena de procesamiento debe resolver. El habla humana pasa por varias etapas de transformación antes de convertirse en una acción en la aplicación.

Pipeline completo de procesamiento de voz — del micrófono a la acción

🎙️

Captura de audio

El micrófono captura ondas de presión sonora y las convierte en señal digital (PCM, 16kHz, 16-bit mono). La detección de actividad de voz (Voice Activity Detection) filtra silencio y ruido de fondo antes de procesar.

SpeechRecognizer.startListening(), AudioRecord, VAD
🔊

Extracción de características

La señal de audio se transforma en representaciones matemáticas manejables por las redes neuronales: espectrogramas Mel (MFCC). Estas son las 'imágenes' del sonido que el modelo de ASR analiza.

Mel-frequency cepstral coefficients (MFCC), STFT
📝

ASR — Speech to Text

El núcleo del sistema. Una red neuronal (generalmente Transformer o RNN-T) convierte el espectrograma en texto. Los modelos modernos como Whisper (OpenAI) funcionan en 99 idiomas con alta precisión, incluso con acentos.

Whisper, wav2vec 2.0, Google ASR, SpeechRecognizer API
🧩

NLP — Natural Language Processing

El texto crudo se parsea para extraer la intención (intent) y las entidades (entities). '¿Qué tiempo hace mañana en Madrid?' → Intent: consultar_tiempo, Entity: {fecha: mañana, ciudad: Madrid}.

DialogFlow, Rasa, Android ML Kit NLU
⚡

Ejecución de la acción

La intención identificada se mapea a una función de la app. La respuesta al usuario puede darse mediante texto en pantalla o síntesis de voz (Text-to-Speech, TTS), cerrando el círculo conversacional.

Android TextToSpeech, Google TTS Engine

Implementación de acciones por voz en Android

Android proporciona la clase SpeechRecognizer que delega el reconocimiento al motor de voz del sistema (normalmente Google Speech Services). También podemos usar el RecognizerIntent para lanzar la interfaz del sistema directamente. Para casos avanzados, podemos integrar Whisper de OpenAI en local.

11class ReconocimientoVozManager(
12    private val context: Context
13) : RecognitionListener {
14
15    // Estado observable del reconocimiento
16    val estado = MutableStateFlow<EstadoVoz>(EstadoVoz.Inactivo)
17
18    private val reconocedor: SpeechRecognizer by lazy {
19        SpeechRecognizer.createSpeechRecognizer(context)
20            .also { it.setRecognitionListener(this) }
21    }
22
23    private val tts: TextToSpeech by lazy {
24        TextToSpeech(context) { status ->
25            if (status == TextToSpeech.SUCCESS) {
26                tts.language = Locale("es", "ES")  // Español de España
27                tts.setSpeechRate(0.9f)             // Un poco más lento que el default
28            }
29        }
30    }
31
32    // ── Iniciar escucha ──────────────────────────────────────────
33    fun iniciarEscucha() {
34        if (!SpeechRecognizer.isRecognitionAvailable(context)) {
35            estado.value = EstadoVoz.Error("El reconocimiento de voz no está disponible")
36            return
37        }
38
39        val intent = Intent(RecognizerIntent.ACTION_RECOGNIZE_SPEECH).apply {
40            putExtra(RecognizerIntent.EXTRA_LANGUAGE_MODEL,
41                     RecognizerIntent.LANGUAGE_MODEL_FREE_FORM) // Lenguaje libre (no comandos fijos)
42            putExtra(RecognizerIntent.EXTRA_LANGUAGE, "es-ES")  // Español
43            putExtra(RecognizerIntent.EXTRA_MAX_RESULTS, 3)     // 3 alternativas de transcripción
44            putExtra(RecognizerIntent.EXTRA_PARTIAL_RESULTS, true) // Resultados parciales en tiempo real
45            putExtra(RecognizerIntent.EXTRA_SPEECH_INPUT_MINIMUM_LENGTH_MILLIS, 500L)
46            putExtra(RecognizerIntent.EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS, 1500L)
47        }
48
49        reconocedor.startListening(intent)
50        estado.value = EstadoVoz.Escuchando
51    }
52
53    fun detenerEscucha() {
54        reconocedor.stopListening()

56    }

Detección de movimiento corporal

La detección de movimiento corporal es la capacidad de una aplicación para entender la posición y el movimiento del cuerpo o las manos del usuario a través de la cámara. Permite crear interfaces que se controlan sin tocar la pantalla, abriendo posibilidades únicas en accesibilidad, deportes, salud y entretenimiento.

La clave técnica es la estimación de pose (Pose Estimation): el proceso de localizar puntos clave del cuerpo (articulaciones) en una imagen o video. Herramientas modernas como MediaPipe Pose hacen esto a 30+ FPS en un smartphone de gama media, lo que hace viable la interacción en tiempo real.

Reconocimiento de gestos con las manos

MediaPipe HandLandmarker detecta 21 puntos clave (landmarks) en 3D de cada mano visible en la imagen. Cada punto tiene coordenadas (x, y, z) normalizadas. Con estos 63 valores numéricos por mano, podemos calcular geometrías, clasificar gestos o enviar comandos a la aplicación.

Los 21 landmarks de MediaPipe HandLandmarker — mapa de puntos

0Muñeca
1–4Pulgar (base → punta)
5–8Índice (nudillo → punta)
9–12Corazón (nudillo → punta)
13–16Anular (nudillo → punta)
17–20Meñique (nudillo → punta)

Cada punto tiene:

x: posición horizontal (0.0 – 1.0)
y: posición vertical (0.0 – 1.0)
z: profundidad (negativo = más cerca)

1import com.google.mediapipe.tasks.components.containers.NormalizedLandmark
2import kotlin.math.*
3
4object AnalizadorPostura {
5
6    // Calcula el ángulo en grados del punto B respecto a A y C
7    // Muy útil para calcular el ángulo de una articulación
8    fun calcularAngulo(
9        a: NormalizedLandmark,  // Punto proximal (hombro)
10        b: NormalizedLandmark,  // Articulación a medir (codo)
11        c: NormalizedLandmark   // Punto distal (muñeca)
12    ): Double {
13        val radians = atan2(c.y() - b.y(), c.x() - b.x()) -
14                      atan2(a.y() - b.y(), a.x() - b.x())
15        var angulo = abs(radians * 180.0 / PI)
16        if (angulo > 180.0) angulo = 360 - angulo
17        return angulo
18    }
19
20    // Detecta si el usuario está haciendo una sentadilla correctamente
21    data class AnalisisPostura(
22        val anguloCaderas: Double,
23        val anguloRodillaIzq: Double,
24        val anguloRodillaDer: Double,
25        val estado: EstadoEjercicio,
26        val feedback: String
27    )
28
29    enum class EstadoEjercicio { ARRIBA, BAJANDO, ABAJO, SUBIENDO, POSICION_INCORRECTA }
30
31    fun analizarSentadilla(landmarks: List<NormalizedLandmark>): AnalisisPostura {
32        // Índices según MediaPipe BlazePose:
33        val hombroIzq  = landmarks[11]; val hombroDer  = landmarks[12]
34        val caderaIzq  = landmarks[23]; val caderaDer  = landmarks[24]
35        val rodillaIzq = landmarks[25]; val rodillaDer = landmarks[26]
36        val tobilloIzq = landmarks[27]; val tobilloDer = landmarks[28]
37
38        val anguloRodillaIzq = calcularAngulo(caderaIzq, rodillaIzq, tobilloIzq)
39        val anguloRodillaDer = calcularAngulo(caderaDer, rodillaDer, tobilloDer)
40        val anguloCaderas    = calcularAngulo(hombroIzq, caderaIzq, rodillaIzq)
41
42        val anguloRodillaMedia = (anguloRodillaIzq + anguloRodillaDer) / 2
43
44        val (estado, feedback) = when {
45            anguloRodillaMedia > 160                 -> EstadoEjercicio.ARRIBA   to "De pie — inicia la sentadilla"
46            anguloRodillaMedia in 90.0..160.0        -> EstadoEjercicio.BAJANDO  to "Bajando bien, mantén la espalda recta"
47            anguloRodillaMedia < 90                  -> EstadoEjercicio.ABAJO    to "¡Posición baja! Ahora sube"
48            anguloCaderas < 45                       -> EstadoEjercicio.POSICION_INCORRECTA to "⚠ Espalda demasiado inclinada"
49            else                                     -> EstadoEjercicio.SUBIENDO to "Subiendo..."
50        }
51
52        return AnalisisPostura(anguloCaderas, anguloRodillaIzq, anguloRodillaDer, estado, feedback)
53    }

55    // Contador de repeticiones de un ejercicio
56    class ContadorRepeticiones(
57        private val umbralAbajo: Double = 90.0,
58        private val umbralArriba: Double = 160.0
59    ) {
60        var repeticiones = 0; private set
61        private var estadoAnterior = EstadoEjercicio.ARRIBA
62
63        fun actualizar(anguloActual: Double) {
64            val estadoActual = when {
65                anguloActual < umbralAbajo  -> EstadoEjercicio.ABAJO
66                anguloActual > umbralArriba -> EstadoEjercicio.ARRIBA
67                else                        -> estadoAnterior
68            }
69            // Cuenta una repetición cuando pasa de ABAJO a ARRIBA
70            if (estadoAnterior == EstadoEjercicio.ABAJO && estadoActual == EstadoEjercicio.ARRIBA) {
71                repeticiones++
72            }
73            estadoAnterior = estadoActual
74        }
75    }

Rendimiento y batería — consideraciones críticas

El procesamiento de cámara en tiempo real con ML es intensivo en CPU/GPU. En producción, debes: (1) reducir la resolución del frame de análisis (no necesitas 4K para detectar gestos — 480p es suficiente), (2) liberar los recursos de la cámara y el detector cuando la app pase a segundo plano (lifecycle-aware), (3) usar aceleración GPU con Delegate.GPU, y (4) considerar saltar frames analizando 1 de cada 2 o 3 si el gesto no requiere reactividad inmediata.


Realidad aumentada

La Realidad Aumentada (AR) es la tecnología que superpone elementos digitales — objetos 3D, texto, anotaciones, animaciones — sobre la vista del mundo real en tiempo real. A diferencia de la Realidad Virtual (VR), que sumerge al usuario en un mundo completamente sintético, la AR mantiene el mundo físico visible y lo enriquece con información o elementos digitales.

Para un desarrollador Android, la herramienta principal es ARCore, el SDK de Google que proporciona las capacidades de percepción del entorno que hacen posible la AR: rastrear la posición del dispositivo, detectar superficies planas, estimar la iluminación y anclar objetos virtuales al mundo real.

Conceptos básicos de realidad aumentada

Los 5 pilares técnicos de la realidad aumentada en Android

📍

Tracking (Seguimiento de posición)

ARCore rastrea continuamente la posición y orientación del dispositivo en el espacio 3D (6 grados de libertad: x, y, z + pitch, yaw, roll). Usa la combinación de IMU (acelerómetro + giroscopio) y análisis visual de la imagen de la cámara (Visual Inertial Odometry). Esto permite que los objetos AR permanezcan 'fijos' en el mundo aunque el usuario mueva el teléfono.

Precisión de seguimiento: sub-centimétrico en condiciones óptimas
🟩

Plane Detection (Detección de planos)

ARCore analiza los features visuales de la imagen para identificar superficies planas: suelos, mesas, paredes. Clasifica los planos como HORIZONTAL_UPWARD_FACING (mesa), HORIZONTAL_DOWNWARD_FACING (techo) o VERTICAL (pared). Los planos detectados son el 'suelo' sobre el que colocar los objetos AR.

La detección mejora con más textura en la superficie (mejor en suelos con patrón que en suelos de color liso)
⚓

Anchors (Anclas en el mundo real)

Una vez detectado un plano, podemos crear un Anchor: un punto fijo en el espacio del mundo real al que 'atar' nuestro objeto 3D. El Anchor mantiene la pose (posición + rotación) del objeto aunque el usuario se mueva. ARCore actualiza continuamente la posición del Anchor para compensar la deriva del tracking.

Los Anchors Persistent pueden guardarse y recuperarse en sesiones futuras (Cloud Anchors para AR multiusuario)
💡

Light Estimation (Estimación de iluminación)

Para que los objetos AR parezcan naturales, deben tener las mismas sombras y reflejos que el entorno real. ARCore analiza la imagen de la cámara para estimar la intensidad y dirección de la luz ambiental, incluyendo armónicos esféricos para simular luz difusa compleja. El resultado se aplica al shader del objeto 3D.

Sin estimación de luz, los objetos AR se ven 'plásticos' y artificiales
📐

Depth API (Mapa de profundidad)

En dispositivos compatibles (con sensor ToF o stereo cameras), ARCore puede generar un mapa de profundidad pixel a pixel. Esto permite oclusión real: que el objeto AR desaparezca detrás de objetos físicos reales (una silla tapa parte del objeto virtual colocado detrás). Es la diferencia entre AR 'pasted' y AR inmersiva.

Disponible en Google Pixel 4+, Samsung S20+, y otros dispositivos con sensor de profundidad

Tipos de realidad aumentada — según cómo se anclan los elementos

Marker-based AR

Un marcador físico (imagen, QR, código Aruco) actúa como sistema de coordenadas. El objeto AR aparece sobre el marcador cuando la cámara lo detecta.

✓Muy preciso y sin deriva de tracking
✗Requiere imprimir/mostrar el marcador
Ej: Instrucciones de montaje sobre piezas con código QR

Markerless AR

No se necesita un marcador impreso. ARCore detecta el entorno (planos, objetos) y ancla los elementos a esas superficies reales. La experiencia es más natural.

✓Funciona en cualquier entorno sin preparación
✗El tracking puede derivar en espacios grandes
Ej: IKEA Place — colocar muebles virtuales en tu habitación

Location-based AR

Los elementos AR se anclan a coordenadas GPS del mundo real. Usan el GPS, brújula y ARCore para posicionar elementos en el mundo.

✓Funciona en exteriores a gran escala
✗El GPS no es preciso a escala de centímetros
Ej: Pokémon GO, Google Maps AR, puntos de interés turísticos

Ejemplo resuelto: manos libres en una app de recetas

Una aplicación de recetas quiere que se pueda usar con las manos manchadas de harina. El diseño de la interacción natural, de principio a fin:

  1. Casos de uso: pasar al paso siguiente o anterior, repetir el paso, poner un temporizador («avísame en 10 minutos») y consultar un ingrediente («¿cuánta harina?»).
  2. Dos canales: voz como canal principal y un gesto de la mano frente a la cámara (deslizar en el aire) como alternativa cuando hay ruido; la pantalla táctil sigue funcionando siempre.
  3. Gramática pequeña y tolerante: «siguiente», «adelante», «vale» → avanzar; «atrás», «anterior» → retroceder; temporizadores con número y unidad. Se normaliza el texto (minúsculas, sin tildes) como en el reto del intérprete.
  4. Palabra de activación o botón grande para empezar a escuchar: escuchar siempre gasta batería y genera falsos positivos. El micrófono solo se activa con la receta en modo cocina.
  5. Respuesta en varios canales: se lee el paso en voz alta (TextToSpeech), se resalta en pantalla y se vibra al terminar el temporizador.
  6. Errores: si no entiende, lo dice y sugiere una orden («Puedes decir “siguiente” o “repite”»); las acciones con consecuencias (borrar una receta) piden confirmación.
  7. Privacidad y rendimiento: reconocimiento en el dispositivo (sin enviar audio a la nube), detección de manos con MediaPipe a baja resolución y solo con la cámara activada por el usuario, permisos pedidos en el momento de usarlos y explicados.
  8. Pruebas con usuarios en una cocina real: ruido del extractor, distancia a la tableta, acentos distintos. Se mide la tasa de órdenes entendidas a la primera.

Un detector de gestos (GestureDetector en Android, o los eventos de puntero en JavaFX y en la web) decide qué ha hecho el dedo a partir de sus posiciones. Cada gesto es un bloque de líneas «tiempo_ms x y» (de que el dedo toca a que se levanta), y los gestos se separan con una línea en blanco. Con el primer y el último punto calcula la distancia (Math.hypot), la duración y la velocidad (px/ms). Clasifica: si la distancia es menor que 10 px, «TOQUE» (menos de 300 ms), «PULSACIÓN LARGA» (500 ms o más) o «INDECISO» (entre medias); si es de al menos 50 px y la velocidad de al menos 0.3 px/ms, un deslizamiento en la dirección del eje dominante: «DESLIZAR DERECHA/IZQUIERDA» si |dx| ≥ |dy| o «DESLIZAR ABAJO/ARRIBA» (la y crece hacia abajo en la pantalla); en otro caso, «ARRASTRE». Muestra «Gesto N: TIPO (D px en T ms, V px/ms)» con D y T sin decimales y V con 2.

Java¿Qué gesto hace la mano?Muy difícil

Los detectores de manos (MediaPipe Hands, ML Kit) devuelven las coordenadas de 21 puntos de la mano. Aquí recibes 11 por mano, en coordenadas normalizadas (de 0 a 1, la y hacia abajo): «muneca x y» y, para cada dedo (pulgar, indice, corazon, anular, menique), su punta («dedo_punta x y») y su articulación media («dedo_medio x y»). Las manos se separan con «---». Un dedo está extendido si su punta está más lejos de la muñeca que su articulación media multiplicada por 1.15 (1.1 en el pulgar): así no importa cómo esté girada la mano. Hay PINZA si la distancia entre las puntas del pulgar y del índice es menor que 0.25 veces la distancia de la muñeca a la articulación media del índice. Gestos, en este orden: PINZA, PUÑO (ningún dedo extendido), MANO ABIERTA (los cinco), PULGAR (solo el pulgar), VICTORIA (solo índice y corazón), SEÑALAR (solo el índice) o DESCONOCIDO. Muestra «Mano N: GESTO (extendidos: dedo1, dedo2…)», con los dedos en el orden del array DEDOS o «ninguno».

Errores típicos

  • Hacer la voz o los gestos el único modo de uso: siempre debe haber alternativa táctil o de teclado (accesibilidad y entornos ruidosos).
  • Gramáticas rígidas que solo entienden una frase exacta.
  • Ejecutar sin confirmar acciones destructivas a partir de un reconocimiento que puede fallar.
  • No dar respuesta: el usuario no sabe si se le ha oído o si se ha detectado su gesto.
  • Comparar coordenadas absolutas en vez de relativas (la mano girada, más cerca o más lejos de la cámara).
  • Enviar audio o imagen a la nube sin necesidad ni consentimiento, o pedir todos los permisos al arrancar.
  • Procesar cada fotograma a máxima resolución en el hilo principal: la interfaz va a saltos y la batería se agota.
