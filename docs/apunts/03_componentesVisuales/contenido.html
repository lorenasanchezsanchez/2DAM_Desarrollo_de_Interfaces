Concepto de componente visual reutilizable

Imagina que estás construyendo una aplicación Android con diez pantallas distintas. En ocho de ellas aparece una tarjeta de usuario con avatar, nombre y estado. Si copias y pegas el código de esa tarjeta ocho veces, cuando el diseño cambie tendrás que modificar ocho ficheros distintos — y seguramente olvides alguno. Este es exactamente el problema que resuelven los componentes visuales reutilizables: encapsulan una pieza de UI en una unidad autocontenida que puede instanciarse tantas veces como sea necesario, configurarse con distintos datos y mantenerse desde un único punto.

Un componente visual reutilizable es una caja negra de UI: tiene una interfaz pública bien definida (sus propiedades y métodos), oculta los detalles de implementación y produce un resultado visual consistente independientemente de dónde se use. Este principio es la base del desarrollo moderno en todas las plataformas: Android Compose, React, Vue, SwiftUI y Flutter están construidos enteramente alrededor de esta idea.

Sin componentes vs. con componentes — el impacto real en el código

✗ Sin componentes — código duplicado

// Fragment A — PantallaInicio.kt
Card { Row { AsyncImage(...) Text(usuario.nombre) } }
Badge { Text(usuario.estado) }

// Fragment B — PantallaAmigos.kt
Card { Row { AsyncImage(...) Text(usuario.nombre) } }
Badge { Text(usuario.estado) }

Cambiar el diseño = modificar N ficheros. Un bug se reproduce N veces.

✓ Con componente — definir una vez, usar en todos lados

// components/TarjetaUsuario.kt
@Composable fun TarjetaUsuario(usuario: Usuario) {
Card { Row { ... } }
}

// Cualquier pantalla:
TarjetaUsuario(usuario = currentUser)
TarjetaUsuario(usuario = amigo)

✓ Cambiar el diseño = modificar 1 fichero. El fix se propaga automáticamente.

Características de un componente visual bien diseñado

No cualquier trozo de UI extraído a una función merece el nombre de componente bien diseñado. Un componente de calidad profesional reúne características que garantizan que será fácil de usar, mantener y extender en el tiempo.

📦

Encapsulamiento

La implementación interna es privada. El consumidor del componente solo necesita conocer su interfaz pública (propiedades y métodos). Los detalles de cómo dibuja el fondo, anima la transición o calcula el tamaño del texto son irrelevantes desde fuera.

Ejemplo: La app solo sabe que existe TarjetaUsuario(usuario). No sabe que usa AsyncImage + Coil internamente.
🎯

Cohesión

El componente tiene una única responsabilidad bien definida. Hace una sola cosa y la hace bien. Si necesita 15 propiedades para configurarse, probablemente está haciendo demasiadas cosas y debería dividirse.

Ejemplo: TarjetaUsuario muestra datos de usuario. No también lista sus publicaciones, ni gestiona el login.
⚙️

Configurabilidad

El componente acepta datos de entrada a través de propiedades bien definidas. Valores por defecto razonables lo hacen usable sin configuración, pero permite personalización cuando es necesario.

Ejemplo: TarjetaUsuario(usuario, mostrarEstado = true, tamaño = TamañoTarjeta.NORMAL)
🔓

Independencia de contexto

El componente no asume nada sobre dónde se usa. No accede directamente a ViewModels globales ni bases de datos. Los datos llegan por propiedades y comunica eventos hacia fuera por callbacks.

Ejemplo: TarjetaUsuario no llama a ViewModel ni a Room. Recibe el usuario por parámetro.
🧪

Testabilidad

Al ser independiente del contexto, el componente se puede probar en aislamiento. En Jetpack Compose con createAndroidComposeRule pasando datos de prueba directamente al componente.

Ejemplo: composeTestRule.setContent { TarjetaUsuario(usuarioDePrueba) }
🧩

Composabilidad

Los componentes simples se combinan para crear componentes más complejos. Un componente complejo es una composición de otros más simples — el principio LEGO aplicado a UI.

Ejemplo: PantallaInicio = Scaffold + BarraBusqueda + Lista(TarjetaUsuario)

El diseño modular — construir la interfaz como una jerarquía de componentes independientes en lugar de pantallas monolíticas — tiene un impacto directo y medible en la calidad del software y la productividad del equipo de desarrollo.

Atomic Design — el marco conceptual del diseño modular

La jerarquía que acabamos de ver está inspirada en el Atomic Design de Brad Frost (2013), una metodología adoptada en la industria para organizar los sistemas de diseño y sus implementaciones en código. Aunque la terminología varía entre plataformas (Compose usa "Composable", React usa "Component", Vue usa "Component"), el principio es universal: construir de lo más simple a lo más complejo, reutilizando y componiendo en cada nivel.


Desarrollo de componentes visuales

Crear un componente reutilizable de calidad requiere pensar cuidadosamente en tres aspectos antes de escribir la primera línea de código: qué propiedades necesita para ser configurable, qué métodos expone hacia el exterior, y cómo gestiona los eventos del usuario para comunicarlos al código que lo usa.

Definición de propiedades

Las propiedades son los parámetros que el componente recibe de su padre para configurar su apariencia y comportamiento. En Jetpack Compose son los parámetros de la función @Composable. En el sistema de Views clásico, se declaran como atributos XML en un declare-styleable y se leen vía TypedArray en el constructor.

Cuatro tipos de propiedades que todo componente puede tener

Estrategia de valores por defecto — el principio de la menor sorpresa

✓ Buenas prácticas

El caso más común es el default

Si el 90% de los usos son con variante PRIMARIO, ese debe ser el default. El consumidor solo especifica lo que difiere.

Modifier vacío siempre disponible

modifier: Modifier = Modifier permite al consumidor modificar tamaño, padding y posición sin necesidad de un wrapper.

Callbacks opcionales nullable

onClick: (() -> Unit)? = null permite componentes no interactivos. Verifica null antes de llamar al callback.

Strings desde recursos R

En vez de texto = 'Guardar', usa stringResource(R.string.guardar) para soportar múltiples idiomas.

✗ Anti-patrones a evitar

Demasiados parámetros obligatorios

Si el componente exige 8 parámetros sin defaults, agrúpalos en una data class de configuración.

Context como parámetro

Un Composable no debe recibir Context. Usa LocalContext.current internamente si lo necesita.

Estado interno no expuesto

Si el padre necesita controlar el estado (ej: texto de un campo), usa State Hoisting.

Defaults que cambian entre versiones

Si cambias un valor por defecto en una actualización, romperás todos los usos existentes silenciosamente.

Gestión de eventos — State Hoisting en Jetpack Compose

En Jetpack Compose, el patrón fundamental para gestionar eventos es el State Hoisting (elevación del estado). El estado sube al nivel más alto que lo necesita. El componente es stateless y recibe tanto el estado como los callbacks. Esto hace que sea completamente predecible y fácil de probar.

Stateful vs Stateless — cuándo usar cada patrón

Stateful — el componente gestiona su propio estado

El componente tiene estado interno con remember. Conveniente pero dificulta testing y control externo. Usar solo cuando el padre nunca necesita conocer ese estado.

kotlin 
1// ✗ El padre no puede controlar si la contraseña es visible
2@Composable
3fun CampoContrasenaSF() {
4    var visible by remember { mutableStateOf(false) }
5    OutlinedTextField(
6        value = "",
7        onValueChange = {},
8        visualTransformation = if (visible)
9            VisualTransformation.None
10        else PasswordVisualTransformation(),
11        trailingIcon = {
12            IconButton(onClick = { visible = !visible }) {
13                Icon(if (visible) Icons.Default.VisibilityOff
14                     else Icons.Default.Visibility, null)
15            }
16        }
17    )
18    // El padre NO puede controlar externamente la visibilidad
19}

⬆️ Stateless + State Hoisting — el padre controla el estado

El estado sube al padre. El componente es una función pura: dado el mismo estado, produce la misma UI. Patrón recomendado para componentes reutilizables y testables.

Persistencia del componente

Un componente visual puede tener estado que el usuario configura y que queremos que sobreviva: la posición de un panel, las columnas elegidas en una tabla, el nivel de zoom. La persistencia del componenteabarca dos mecanismos según el alcance temporal: la serialización para el estado de la sesión actual (sobrevive a rotaciones de pantalla) y la configuración guardadapara el estado que debe persistir entre sesiones de uso.

Serialización — supervivencia al cambio de configuración

Cuando el usuario rota el dispositivo, Android destruye y recrea la Activity. Si el estado vive solo en variables locales del Composable, se pierde. Hay tres mecanismos para evitarlo, cada uno con su alcance:

rememberSaveable — para tipos primitivos

✓ Sobrevive a rotación y a proceso muerto restaurado

Cuándo usar: Estado simple: posición de scroll, texto escrito, tab seleccionado, valores numéricos.

kotlin

3var textoFiltro by rememberSaveable { mutableStateOf("") }
4var tabSeleccionado by rememberSaveable { mutableStateOf(0) }
5
6// NOTA: para tipos NO primitivos necesitas un Saver personalizado

rememberSaveable + Saver personalizado — para data classes

✓ Sobrevive a rotación y proceso muerto (Bundle)

Cuándo usar: Estado complejo (data class) del componente que debe sobrevivir a proceso muerto.

kotlin 
1data class EstadoFiltro(val texto: String, val orden: OrdenLista, val soloFavoritos: Boolean)

Configuración guardada — DataStore para persistencia entre sesiones

Cuando el usuario cierra la app y la vuelve a abrir, el ViewModel ya no existe. Para que las preferencias del componente sobrevivan entre sesiones, necesitamos almacenamiento persistente. En Android moderno, la solución recomendada es DataStore, el sucesor de SharedPreferences: asíncrono, seguro en hilos y basado en Flow.

SharedPreferences vs DataStore — usa DataStore en proyectos nuevos

SharedPreferences es la API antigua: síncrona y puede causar ANRs en el hilo principal. Jetpack DataStore es su sucesor: totalmente asíncrono con corrutinas y Flow, seguro en hilos, resistente a fallos de IO y con soporte para migración desde SharedPreferences. Úsalo siempre en proyectos nuevos.

TDD aplicado a componentes — Red → Green → Refactor

Una técnica poderosa para desarrollar componentes reutilizables es el Test Driven Development (TDD): escribes primero el test que describe el comportamiento esperado, luego implementas el componente hasta que el test pase. El ciclo es: Rojo (el test falla porque el código no existe) → Verde (implementas lo mínimo para que el test pase) → Refactor (mejoras el código sin romper los tests). Aplicado a componentes, garantiza que cada característica tiene cobertura de test desde el principio.

Las propiedades de JavaFX (IntegerProperty, StringProperty…) avisan a sus oyentes cuando cambian y se pueden enlazar: una propiedad enlazada con bind sigue siempre el valor de otra. Implementa Propiedad (valor inicial 0) para que funcionen las órdenes: «set P v» cambia el valor (si P está enlazada, muestra «ERROR: P está enlazada a Q y no se puede cambiar»); «escuchar P» añade un oyente; «bind P Q» enlaza P a Q (P toma el valor de Q y lo sigue en adelante; si crearía un ciclo, «ERROR: enlace circular»); «unbind P» rompe el enlace; y «get P» muestra «P = valor». Los componentes de entrada con máscara (fechas, teléfonos, matrículas) solo aceptan caracteres válidos e insertan solos los separadores. Al escribir, primero se añaden los literales que haya antes del siguiente hueco; si la tecla no encaja con el hueco, se rechaza «(se esperaba un dígito)» o «(se esperaba una letra)»; si la máscara ya está llena, «(campo completo)». BORRAR quita el último carácter y, además, los literales que queden al final. Errores típicos

  • Componentes que dependen de la pantalla donde se usan (acceden a datos globales o a otros controles): dejan de ser reutilizables.
  • Estado escondido dentro del componente que el padre no puede controlar (en Compose, no aplicar «state hoisting»).
  • Avisar de cambios que no son cambios: listeners que se disparan con el mismo valor y provocan bucles o redibujados inútiles.
  • Estilos fijos en el código en lugar de clases CSS o temas: el componente no se adapta al tema oscuro ni a la marca.
  • No guardar el estado al girar el dispositivo o al recrear la vista.
  • Publicar una librería sin documentación de sus propiedades, eventos y ejemplos de uso.
  • Olvidar la accesibilidad: un componente dibujado a mano no tiene nombre accesible ni se maneja con teclado si no se programa.
