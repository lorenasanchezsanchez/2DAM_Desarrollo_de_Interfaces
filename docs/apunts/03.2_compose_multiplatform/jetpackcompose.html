Las prácticas originales de Android serán el punto de partida: reconstruiremos sus aplicaciones con Compose Multiplatform y comprobaremos el resultado en escritorio. No es necesario haber cursado Android ni conocer Kotlin o Compose; introduciremos cada concepto antes de utilizarlo.

Crearemos el proyecto multiplataforma desde cero y, dentro de este mismo proyecto, reconstruiremos primero Hola Compose, després el contador de vidas i la Filmoteca. Les aplicacions originals d’Android ens serviran de referència: distingirem què podem compartir i què necessita una adaptació per a escriptori. Després afegirem Colección Pokémon como práctica propia para aprender bases de datos relacionales. Incivismo y Notas de voz quedan fuera de este recorrido: dependen de servicios del móvil que requerirían una unidad específica para cada plataforma.

Este es un itinerario independiente de las prácticas de Android y de Diseño de Videojuegos. Tiene una planificación y una impartición propias. Usaremos las aplicaciones Android originales como referencia de lo que construiremos, sin dar por hecho que el alumnado ya las ha realizado. Empezaremos con Android y escritorio; iOS y web quedarán como ampliaciones.

Qué aprenderemos

  • Preparar un destino de escritorio y comprobar una aplicación Compose en una ventana de escritorio.
  • Adaptar progressivament les aplicacions mòbils del curs, començant per Hola Compose i el contador de vidas.
  • Reconocer qué interfaz y lógica podemos compartir y qué partes dependen de Android.
  • Ajustar las interfaces para que funcionen con los tamaños y las interacciones propias de una ventana de escritorio.

Antes de empezar: palabras que utilizaremos

No es necesario haber creado antes una aplicación Android ni haber trabajado con Compose Multiplatform. La práctica inicial presenta el proyecto y los componentes Compose desde el principio; las expresiones básicas de Kotlin se explican cuando aparecen. Conocer Kotlin o Compose puede ayudar, pero no es un requisito para seguir el itinerario.

Término Qué significa en esta unidad
Plataforma El sistema en el que se ejecuta el programa. En nuestro proyecto son Android y escritorio (Desktop/JVM).
Interfície compartida Código Kotlin y Compose compilado para más de una plataforma, guardado en shared/src/commonMain.
Codi específic El poco código de arranque o acceso a servicios del sistema que necesita cada plataforma, guardado en androidApp, desktopApp o un source set com androidMain.
Source set Una carpeta de código con una lista concreta de plataformas en las que se puede compilar ese código. commonMain es compartido; androidMain solo es para Android; jvmMain és per a Desktop/JVM.
Dependència Una biblioteca externa que el proyecto descarga y añade a la compilación, por ejemplo, Coil para imágenes.

Compose Multiplatform no convierte Android en Desktop ni hace que todos los servicios del sistema sean iguales. Lo primero que compartimos es la interfaz y la lógica escrita en Kotlin común. Android abre esa interfaz desde una Activity; Desktop la abre desde una función main dentro de una ventana. Más adelante, cuando leamos imágenes o hagamos una petición HTTP, añadiremos Ktor al código compartido para que funcione en ambas plataformas.

Quan aparega codi que comença per androidx, eso no significa automáticamente que sea exclusivo de Android: Compose Multiplatform reutiliza algunas bibliotecas con ese nombre. Nos fijaremos en qué source set declara cada dependencia y comprobaremos siempre que compila para los dos destinos.

Guía breve para el profesorado

La guía también está pensada para un profesor que todavía no haya trabajado con Compose. No presuponemos que conozca el modelo mental de Compose ni las API de Android: las lecciones presentan cada idea antes del primer uso y la comprueban con un cambio visible en la aplicación. No es necesario explicar el ciclo completo de una app Android ni las API nativas para impartir este recorrido.

Cómo leer una pantalla Compose

Se puede seguir el código desde App() hasta los componentes visibles, sin estudiar primero toda la plataforma:

  1. Una funció amb @Composable, com HolaCompose(), describe una parte de la interfaz.
  2. Els components dins de la funció (Text, Button, Row, Column) forman el árbol visual. El código Kotlin expresa qué se debe mostrar y cómo se organiza.
  3. Els paràmetres i Modifier ajustan los componentes: por ejemplo, el texto que muestra un Text o el espacio que ocupa una Column.
  4. Cuando la pantalla necesita recordar un dato, remember i mutableStateOf mantienen ese valor mientras la pantalla está abierta. Un evento como escribir o pulsar un botón puede cambiarlo.
  5. Si Compose detecta que cambia un estado leído por la pantalla, vuelve a ejecutar la función necesaria y actualiza lo que se ve. Este proceso se llama recomposició; no es necesario modificar manualmente un componente ya dibujado.

En 2. se ve este recorrido en una pantalla breve: primero añadimos textos y controles fijos, después conectamos el campo a un estado y, al final, hacemos que el botón actualice el mensaje. En 3 el componente padre guarda las vidas y pasa a cada tarjeta los valores y las acciones. Así se puede explicar el código de forma práctica antes de introducir términos como estado elevado o UDF.

Conceptos de plataforma que aparecen

Basta con presentar estos puntos cuando aparezcan:

  • Activity: la ventana principal que abre Android. El proyecto la crea; en esta práctica solo hacemos que invoque el composable común.
  • AndroidManifest.xml: información de la app Android. Declaramos allí el permiso de Internet cuando cargamos imágenes o hacemos peticiones; no es una pantalla ni código Compose.
  • Emulador: un dispositivo Android virtual. Es solo uno de los lugares donde ejecutar y comparar la misma interfaz.
  • Desktop/JVM: el programa de escritorio y la ventana equivalentes a la Activity y la pantalla de Android.
  • commonMain: el código que queremos probar en ambos. Si aparece una API que solo compila en un destino, no la ponemos aquí; buscamos una biblioteca multiplataforma o la dejamos en el source set específico.

Las páginas explican estos términos cuando el código los necesita. Gradle, Ktor, Coil y DataStore se introducen solo en la fase que los requiere. Si el profesor no ha utilizado alguna de estas herramientas, puede seguir los pasos desde el resultado de comprobación anterior; no necesita preparar una explicación adicional de arquitectura.

Para guardar datos utilizamos la herramienta que corresponde a cada necesidad: DataStore conserva valores sencillos y el JSON de Filmoteca; Room guarda las tablas relacionadas de la colección Pokémon. Así primero aprendemos a persistir preferencias sin introducir SQL y, cuando necesitamos relacionar especies y ejemplares, presentamos Room paso a paso. También se utiliza en aplicaciones Android, pero no es necesario haberla estudiado antes.

Crearemos el esqueleto multiplataforma con el asistente oficial y trasladaremos a él el código de nuestras aplicaciones por partes. Esto nos permite empezar con una configuración generada para Android y Desktop, sin convertir la primera lección en una edición manual de Gradle.

Preparación y plataformas

Utilizaremos el asistente oficial de Kotlin Multiplatform para crear el proyecto con Android y Desktop. Mantendremos las aplicaciones Android del curso como punto de partida y comparación. Empezaremos en 1. Crear el proyecto.

La interfaz de Compose Multiplatform para iOS ya es estable, pero compilar y ejecutar la aplicación iOS requiere un Mac con Xcode. Por eso lo dejamos como ampliación, en lugar de convertirlo en un requisito para toda la clase. La guía oficial también permite seleccionar solo las plataformas que nos interesan.

Ampliaciones posibles

Cuando funcione el contador compartido, podemos añadir iOS en un Mac o explorar el destino web. También podemos probar qué ocurre cuando una aplicación necesita una función propia de una plataforma. Estas ampliaciones llegarán después de haber entendido y comprobado el código compartido.
